## 0. 한눈에 보기

| 단계 | 기간(대략) | 목표 | 통과 기준 |
|---|---|---|---|
| **0. 공모전** | ~11/20 | 데모와 발표 | 서류 통과, 발표 완료 |
| **1. 문제 검증** | 1~2개월 | 정말 아픈 문제인지 확인 | 인터뷰 20명 이상, "돈 내고 쓰겠다"는 팀 3곳 이상 |
| **2. MVP + 파일럿** | 2~3개월 | 실제 팀이 매주 쓰는지 확인 | 디자인 파트너 3~5팀, 4주 연속 사용 |

## 1. 도메인 지식

### 1.1 직무 간 협업 (우리 서비스의 핵심 자산)
번역 품질은 결국 **"각 직무가 무엇을 궁금해하는가"**를 얼마나 정확히 아느냐에 달려 있습니다. 이 지식이 프롬프트와 출력 형식으로 바뀌기 때문에, 사실상 우리의 핵심 경쟁력입니다.

| 알아야 할 것 | 내용 | 얻는 방법 |
|---|---|---|
| 직무별 업무 흐름 | 기획 → 디자인 → 개발 → QA → 배포 → CS가 어떻게 이어지는지 | 현직자 인터뷰, 직무 소개 글, 부트캠프 커리큘럼 |
| 직무별 산출물 | PRD, 와이어프레임, API 명세, 테스트 케이스, 버그 리포트, Jira 티켓 | 실제 템플릿 수집 (Notion, Jira 공개 템플릿) |
| 직무별 용어 | "PG", "풀스캔", "엣지 케이스", "QA 리그레션", "디자인 토큰" 등 | 용어 사전 직접 구축 (G 기능의 씨앗) |
| 자주 생기는 오해 유형 | 일정("이번 주" vs "이번 스프린트"), 범위("간소화"의 의미), 완료 기준 | 인터뷰에서 **실제 사례**를 수집 |
| 숙련도별 차이 | 주니어와 시니어가 필요로 하는 정보의 양과 깊이 | 인터뷰, 사내 온보딩 문서 |

> **할 일:** 인터뷰에서 "최근에 다른 직무와 오해가 생겼던 대화"를 **원문 그대로** 받아두면, 데모 시나리오와 평가 데이터를 동시에 얻을 수 있습니다.

### 1.2 커뮤니케이션 이론과 연구
발표와 투자 설명에서 "왜 이 문제가 진짜인가"를 뒷받침하고, B 기능의 설계 근거가 됩니다.

| 개념 | 의미 | 우리에게 쓰이는 곳 |
|---|---|---|
| 공통 기반 (Common ground, H. Clark) | 대화하는 사람들이 서로 안다고 믿는 정보 | 오해가 생기는 이유를 설명하는 틀 |
| 근거 확인 (Grounding) | 서로 이해했다는 것을 확인하는 과정 | B의 "확인 질문" 설계 |
| 지식의 저주 (Curse of knowledge) | 전문가가 비전문가의 눈높이를 상상하지 못하는 현상 | 기본 번역이 필요한 이유 |
| 숨겨진 의견 불일치 연구 | arXiv 2608.08210 (회의당 평균 2.89개) | 문제의 크기를 보여주는 근거 |

### 1.3 시장과 업계
| 알아야 할 것 | 왜 필요한가 |
|---|---|
| Slack 생태계: 요금제, 앱 마켓, Slack AI의 발전 방향 | Slack이 같은 기능을 내놓으면 우리 입지가 줄어듦. 이 리스크를 항상 추적해야 함 |
| 국내 협업툴: 잔디, 네이버웍스, 카카오워크, Teams | 국내 시장을 노린다면 Slack만으로는 부족할 수 있음 |
| B2B SaaS 구매 구조 | **쓰는 사람**(팀원), **결제하는 사람**(팀장·대표), **승인하는 사람**(보안·IT 담당)이 다름. 셋 모두를 설득해야 함 |
| 경쟁사 동향 | Grammarly(Superhuman), Momental, Claude Tag 등. 분기마다 다시 확인 |

### 1.4 법·보안·개인정보 (B2B에서는 기능만큼 중요)
회사 메시지를 읽고 처리하는 서비스라서, **고객사 보안 검토를 통과하지 못하면 팔 수 없습니다.**

| 항목 | 내용 | 시점 |
|---|---|---|
| 개인정보보호법 | 메시지 안에 개인정보가 들어 있음. 처리방침 작성, 처리 위탁 고지 필요 | MVP 전 |
| **국외 이전** | 해외 AI API(Claude, OpenAI 등)로 데이터를 보내면 국외 이전에 해당할 수 있음. 고지와 동의 절차 확인 | MVP 전 |
| AI 기본법 ⚠️ | 2026년 1월 시행. 생성형 AI 결과물 표시 의무 등이 해당하는지 확인 | MVP 전 |
| AI 제공사 데이터 정책 | API로 보낸 데이터가 모델 학습에 쓰이지 않는지, 얼마나 보관되는지 확인하고 고객에게 설명 | MVP 전 |
| Slack API 이용약관 ⚠️ | Slack 데이터의 저장, 외부 반출, AI 학습 사용에 제한이 있음 (2025년 개정) | 개발 시작 전 |
| 이용약관, DPA(데이터 처리 계약서) | 고객사가 요구함. 템플릿에서 시작해 전문가 검토 | 첫 유료 고객 전 |
| 보안 인증 (ISMS-P, SOC 2) | 대기업·중견기업 고객은 요구하는 경우가 많음. 스타트업 초기에는 보안 질의서 답변으로 대응 | 성장 단계 |
| 특허 | 조사 문서에 기재한 미국 특허 4건(11817086, 12323473, 11882161, 12141534)의 청구 범위 확인. 우리 아이디어의 특허 출원도 검토 | 창업 전후 |

> **감시 도구 오해 주의:** B(오해 탐지)는 "누가 무엇을 잘못 이해했는지"를 분석하는 기능이라서, **직원 평가나 감시 도구로 받아들여질 위험**이 있습니다. "결과는 참여자에게만 보이고 관리자 평가에는 쓰지 않는다" 같은 원칙을 제품 설계와 약관에 처음부터 넣어야 합니다.

## 2. 기술 스킬

### 2.1 Slack 플랫폼 (가장 먼저 익혀야 할 것)
| 항목 | 내용 |
|---|---|
| Bolt 프레임워크 | Slack 공식 앱 개발 도구 (Python 또는 JavaScript). 처음부터 이걸로 시작 |
| 앱이 사용자와 만나는 방식 | 메시지 단축키(메시지 메뉴 버튼), 슬래시 명령어, 모달(팝업 창), App Home 탭, Block Kit(버튼과 카드 UI) |
| 이벤트 처리 | Events API, 개발할 때는 Socket Mode(서버 공개 주소 없이 테스트 가능) |
| **3초 규칙** | Slack은 요청을 받으면 3초 안에 응답하라고 요구함. AI 호출은 더 오래 걸리므로 "먼저 응답하고, 결과는 나중에 보내는" 구조가 필수 |
| OAuth 설치 | 여러 회사가 설치하려면 워크스페이스별 토큰 저장과 권한(scope) 관리가 필요함 |
| 앱 마켓 심사 | 정식 출시하려면 Slack 마켓플레이스 심사를 통과해야 함 (보안, 개인정보, UX 요구사항) |

**기획에 영향을 주는 Slack의 제약** (11/10 확인 완료. 상세 내용과 출처는 [개발_조사.md](./개발_조사.md) 2장)
1. **A는 앱의 작성 모달에서 실행.** 슬래시 명령어나 전역 단축키로 모달을 열고, 대상 채널·수신자를 선택해 초안을 작성·점검한 뒤 최종 확인하여 보냅니다. Slack 기본 입력창의 초안을 가로채지 않는 흐름이며, 기획안 v1.2에 반영했습니다.
2. **스레드 읽기 제한 ⚠️.** 2025년부터 마켓에 등록되지 않은 앱은 대화 기록 API(`conversations.history`, `conversations.replies`)의 호출 횟수가 크게 제한된다고 알고 있습니다. B(오해 탐지)는 스레드 전체를 읽어야 하므로 **마켓 등록이 사실상 필수**일 수 있습니다.
3. **데이터 저장과 AI 학습 제한 ⚠️.** Slack 데이터를 오래 저장하거나 모델 학습에 쓰는 것이 약관상 제한됩니다. 그래서 "처리만 하고 저장하지 않는" 구조가 기본이 되어야 합니다.

### 2.2 AI(LLM) 엔지니어링
모델을 직접 학습시키지 않고, **범용 AI API를 잘 쓰는 기술**이 핵심입니다.

| 스킬 | 내용 | 우리 기능과의 연결 |
|---|---|---|
| 프롬프트 설계 | 역할, 프로필, 직무별 출력 형식, 예시를 체계적으로 넣는 방법 | 기본 번역, A, D |
| 구조화된 출력 | 결과를 JSON 같은 정해진 형식으로 받기 | B의 "사람별 이해 요약 → 비교" |
| 근거 표시 | 원문에 있는 정보와 AI가 추측한 정보를 구분 | ⚠️ 추측 표시 기능 |
| **평가(Eval)** | 테스트 데이터셋을 만들고, 사람 평가나 AI 채점으로 품질을 수치화 | 모든 기능. **가장 소홀히 하기 쉽지만 가장 중요함** |
| 비용·속도 관리 | 모델 선택(작은 모델 vs 큰 모델), 프롬프트 캐싱, 토큰 절약 | 수익 구조에 직결 (1인당 월 AI 비용 < 요금) |
| 개인정보 가리기 | AI에 보내기 전에 이름, 전화번호 등을 가리는 처리 | 보안 검토 대응 |
| 다국어 | 한국어 ↔ 영어 번역 품질, 용어 일관성 | D |

**B(오해 탐지)의 기술 구조 (조사 8장 반영)**
```
사용자가 "이 스레드 점검" 메시지 단축키 실행 (종료 자동 감지는 초기 범위 제외)
  → AI가 참여자별 "이해했을 내용" 요약 (구조화된 출력)
  → 요약끼리 비교해 어긋나는 항목 후보 선정
  → 참여자 각자에게 객관식 확인 질문 전송 (Slack DM)
  → 답을 비교해 실제 불일치만 표시
```
> AI가 혼자 판단하지 않고 **"AI가 의심 항목을 고르고 → 사람이 확인한다"**는 2단계 구조입니다. 연구에서도 대화만 보고 판단한 정확도는 절반 수준이었기 때문에, 이 구조가 기술적으로도, 발표에서도 핵심입니다.

**평가 데이터셋 만들기 (우리만의 자산)**
- 직접 만든 시나리오를 기본으로 시작 (50~100개). 인터뷰 사례는 제공자의 권한·동의와 데이터 출처별 이용 조건을 확인한 경우만 평가용으로 검토하며, Slack API 메시지를 평가셋에 축적하지 않음
- 각 사례에 "실제로 어긋난 부분"을 정답으로 표시
- 프롬프트나 모델을 바꿀 때마다 이 데이터로 점수를 비교
- 이 평가셋은 프롬프트 품질 비교에 사용. G는 별도로 앱 프로필·피드백·확인 응답·오해 유형 통계만 후보로 검토하며, 파생 데이터 저장·활용 허용 범위 확인 전에는 축적·재사용하지 않음 ([기획안 v1.2의 G](./기획안_v1.md))

### 2.3 백엔드와 인프라
처음에는 **최소한으로** 시작합니다. 사용자가 늘기 전에 복잡한 구조를 만들 필요는 없습니다.

| 항목 | 추천 (초기) | 나중에 고려 |
|---|---|---|
| 언어·프레임워크 | Python + Slack Bolt (AI 관련 자료가 가장 많음) | - |
| DB | PostgreSQL (Supabase 같은 관리형 서비스) | - |
| 저장할 것 | 팀, 사용자 프로필, 용어집, 피드백, 워크스페이스 토큰(암호화) | 오해 통계 (G) |
| **저장하지 않을 것** | 메시지 원문 (처리 후 바로 폐기가 기본) | 고객이 동의한 경우만 |
| 비동기 처리 | 3초 규칙 때문에 필요. 초기엔 Bolt의 지연 응답 기능으로 충분 | 작업 큐 (사용자 증가 시) |
| 배포 | Cloud Run, Fly.io, Railway 등 서버 관리가 적은 서비스 | AWS (고객이 요구 시) |
| 모니터링 | 에러 알림(Sentry), AI 호출 비용과 응답 시간 기록 | - |
| 관리자 화면 | Slack App Home으로 충분 | 웹 대시보드 (G 기능) |

### 2.4 보안 기본기
- Slack 요청 서명 검증 (Bolt가 기본 제공)
- 워크스페이스 토큰 암호화 저장
- 최소 권한(scope)만 요청 (권한이 많으면 마켓 심사와 고객 보안 검토에서 불리)
- 회사(워크스페이스)별 데이터 분리
- 로그에 메시지 원문이 남지 않게 관리

## 3. 제품·창업 스킬

### 3.1 고객 개발 (1단계의 핵심)
| 방법 | 내용 |
|---|---|
| 문제 인터뷰 | 기능을 설명하지 말고 **과거의 실제 경험**을 묻기. ("최근에 다른 직무와 오해가 생긴 적이 있나요? 그때 어떻게 해결했나요? 비용이 얼마나 들었나요?") 참고: 책 *The Mom Test* |
| 대상 | 스타트업 기획자·개발자·디자이너, 해외 개발팀과 일하는 회사, 외주 개발사 |
| 찾을 신호 | 이미 돈이나 시간을 쓰고 있는 문제인가 (회의 추가, 문서 재작성, 재작업) |
| 첫 고객 정하기 | 기획안 7장의 미정 항목. 인터뷰 결과로 결정 |

### 3.2 파일럿 운영 (2단계)
- **디자인 파트너:** 무료로 먼저 써보는 대신 매주 피드백을 주는 팀 3~5곳
- **주간 확인:** 사용 데이터 + 15분 통화
- **측정할 지표:**

| 지표 | 의미 |
|---|---|
| 활성화율 | 설치한 팀 중 첫 주에 실제로 번역을 쓴 비율 |
| 주간 사용량 | 사용자 1인당 주간 번역·점검 횟수 |
| "더 쉽게 / 더 자세히" 비율 | 번역 난이도가 맞는지 보여주는 품질 지표 |
| B 확인율 | 오해 후보 중 사람이 "실제로 어긋났다"고 확인한 비율 (정확도) |
| 4주 유지율 | 4주 뒤에도 쓰는 팀의 비율 (가장 중요) |

### 3.3 비즈니스 모델
| 항목 | 알아야 할 것 |
|---|---|
| 가격 모델 | 1인당 월 구독(Slack과 같은 방식) vs 팀 단위 요금. 무료 체험 → 유료 전환 |
| 단위 경제성 | 1인당 월 AI 비용 + 서버 비용 < 1인당 요금. **AI 비용을 반드시 먼저 계산** |
| 핵심 지표 | 월 반복 매출(MRR), 고객 획득 비용(CAC), 이탈률(Churn), 고객 생애 가치(LTV) |
| 판매 방식 | 초기: 앱 마켓 + 직접 영업(디자인 파트너 → 소개). 이후: 사용자가 퍼뜨리는 구조(번역된 메시지를 받은 사람이 앱을 알게 됨) |

### 3.4 창업 실무
| 항목 | 내용 |
|---|---|
| 정부 지원사업 | 예비창업패키지(창업 전), 초기창업패키지, 청년창업사관학교, 학교 창업지원단 프로그램 |
| 투자 | 엑셀러레이터 → TIPS 연계 → 시드 투자 |
| 법인 설립 | 지원사업이나 계약이 필요해지는 시점에. 지분 구조와 공동창업자 계약을 **먼저** 정리 |
| 팀 역할 | 최소 구성: 제품·고객(인터뷰, 기획), AI·백엔드 개발, Slack 앱·프론트 개발 |
