## 1. 한 줄 정의

**같은 메시지를, 받는 사람의 팀·직무·숙련도·지식 수준에 맞춰 번역해 주는 AI.** 보내기 전에는 오해를 예방하고, 대화가 끝난 뒤에는 서로 다르게 이해한 부분을 잡아냅니다.

> *"Slack explains words. We translate perspectives — before you send, and after you talk."*
> (슬랙은 단어를 설명합니다. 우리는 관점을 번역합니다. 보내기 전에도, 대화가 끝난 뒤에도.)

## 3. 기본 기능: 맞춤 번역

### 3.1 번역 기준 4가지

| 기준 | 의미 | 예시 |
|---|---|---|
| **팀** | 팀의 맥락: 프로젝트, 사용하는 기술, 팀 용어집 | "결제팀 / React + Spring / 'PG' = 결제대행사" |
| **직무** | 받는 사람이 일하는 관점 | 기획, 프론트엔드, 백엔드, UI 디자인, QA, CS |
| **숙련도** | **자기 직무** 안에서의 깊이 | 주니어 / 미들 / 시니어 |
| **지식 수준** | **다른 분야**를 얼마나 아는지 (분야별) | "디자이너지만 프론트엔드 지식 상, 백엔드 지식 하" |

> **숙련도와 지식 수준은 다른 것입니다.** 숙련도는 자기 분야를 얼마나 깊이 아는지, 지식 수준은 다른 분야를 얼마나 아는지입니다.
> 예를 들어 시니어 디자이너라도 백엔드 지식이 낮으면, DB 관련 메시지는 쉽게 풀어서 보여줘야 합니다.

### 3.2 같은 메시지를 다르게 번역한 예

**원문 (백엔드 개발자):** "DB 인덱스가 없어서 검색 쿼리가 풀스캔 돼요. 인덱스 추가하고 캐시 붙일게요."

| 받는 사람 | 번역 결과 |
|---|---|
| 기획자 (시니어, 기술 지식 하) | 검색이 느린 원인을 찾았습니다. 고치는 데 1~2일 걸리고, 출시 일정에는 영향이 없습니다. 기획 쪽에서 결정할 사항은 없습니다. |
| 프론트엔드 개발자 (주니어) | 백엔드 검색 API가 느린 이유는 DB 인덱스가 없어 전체 데이터를 다 읽기(풀스캔) 때문입니다. 인덱스와 캐시를 추가할 예정이고, **API 응답 형식은 바뀌지 않으므로** 프론트 수정은 필요 없습니다. |
| UI 디자이너 (미들, 프론트 지식 상) | 검색 결과가 늦게 뜨는 문제를 고치는 중입니다. 고치기 전까지는 로딩 상태 화면이 길게 보일 수 있으니, 검색 로딩 화면을 한번 점검해 주세요. |

> 위의 "1~2일" 같은 수치는 예시입니다. 실제로는 대화 맥락에 있는 정보만 사용하고, 없는 정보는 AI가 추측했다고 표시합니다 (3.4 참고).

### 3.3 직무별 출력 형식 (기본값, 팀에서 수정 가능)

| 직무 | 받고 싶은 정보 |
|---|---|
| 기획 | 사용자 영향, 일정, 비용, **내가 결정해야 할 것** |
| 개발 | 요구사항, 완료 기준, 예외 상황, 영향받는 API와 화면 |
| 디자인 | 화면 상태(기본, 로딩, 에러, 빈 화면), 사용 흐름, 문구 |
| QA | 테스트할 시나리오, 재현 조건 |
| CS·영업 | 고객에게 어떻게 설명할지, 언제 해결되는지 |

### 3.4 정확성 장치
- **원문 함께 보기:** 번역 결과 아래에 항상 원문을 접어서 표시합니다.
- **추측 표시:** 원문에 없는 내용을 AI가 보완한 부분은 ⚠️ 표시를 붙입니다.
- **난이도 피드백:** "더 쉽게" / "더 자세히" 버튼으로 그 사람의 지식 수준을 자동으로 보정합니다.

### 3.5 프로필 설정 방법
- **처음 설정:** 직무, 숙련도, 분야별 지식 수준을 선택합니다 (30초 안에 끝나는 수준).
- **자동 보정:** "더 쉽게" / "더 자세히" 피드백이 쌓이면 지식 수준을 자동으로 조정합니다.
- **팀 설정:** 관리자가 팀 용어집, 사용하는 기술, 직무별 출력 형식을 등록합니다.

## 4. 메인 기능

### B. 오해 탐지 (대표 기능)
- **언제:** 사용자가 대상 메시지의 메뉴에서 **"이 스레드 점검" 메시지 단축키**를 실행했을 때. 초기 범위에서는 스레드 종료 자동 감지를 제외합니다.
- **하는 일:**
  1. 참여자별로 이렇게 이해했을 것이라는 요약을 만듭니다.
  2. 요약끼리 비교해서 **어긋날 가능성이 있는 후보**를 표시합니다. 예: "출시일: 기획자 = 이번 주 금요일 / 개발자 = 다음 스프린트 ⚠️ (AI 추정)"
  3. 참여자에게 같은 확인 질문을 따로 보내고, 응답이 다를 때 실제 불일치로 표시합니다. 예: "출시일은 이번 주 금요일인가요, 다음 스프린트인가요?" 응답 전에는 후보로만 표시합니다.
- **Slack 구현 근거:** 메시지 단축키는 원본 메시지의 맥락을 전달합니다 ([공식 문서](https://docs.slack.dev/interactivity/implementing-shortcuts/)). 스레드는 실행 시 조회하고 앱에 적용되는 [호출 제한](https://docs.slack.dev/reference/methods/conversations.replies/)에 맞춰 처리합니다. 자동 감지는 이벤트 권한·호출량 검증 후 검토합니다.
- **차별점:** 여러 사람의 이해를 비교해야 해서 AI 없이는 불가능한 기능입니다. 사람 간 해석 차이를 비교하는 상용 서비스는 찾지 못했습니다. 비슷한 쪽으로는 Momental(초기 단계)이 **이미 기록된 결정**과 모순되는 메시지를 표시하므로, 우리는 **결정이 기록되기 전** 사람끼리 다르게 이해한 부분을 다룬다고 구분해서 설명합니다 ([경쟁서비스_조사.md](./경쟁서비스_조사.md) 4장).

### A. 보내기 전 점검 (B 앞의 예방 단계)
- **언제:** 사용자가 슬래시 명령어나 전역 단축키로 앱의 작성 모달을 열었을 때. Slack 기본 입력창의 초안을 가로채는 동작은 초기 범위에 포함하지 않습니다.
- **하는 일:**
  1. 모달에서 전송할 채널과 받는 사람을 선택하고 초안을 작성합니다. 선택한 사람의 등록된 프로필로 직무를 파악합니다.
  2. 직무별로 예상 질문을 보여줍니다. 예: "개발자: 어느 화면인가요? 실패하면 어떻게 하나요?"
  3. 빠진 정보를 체크리스트로 보여줍니다 (화면, 조건, 기한, 우선순위).
  4. "보완하기"를 누르면 AI가 수정안을 제안합니다. 보내는 사람이 최종 확인한 뒤 보냅니다.
- **Slack 구현 근거:** [단축키로 모달 열기](https://docs.slack.dev/interactivity/implementing-shortcuts/)와 [모달 제출 후 메시지 게시](https://docs.slack.dev/surfaces/modals/#publishing-messages-after-modals-are-submitted)는 공식 지원 흐름입니다. 전역 단축키에는 채널·메시지 맥락이 없으므로 모달에서 대상을 선택합니다.
- **차별점:** Grammarly Reader Reactions가 상대방 한 명의 반응을 미리 예측하고, Teams Copilot은 어조만 조정합니다. 우리는 **받는 사람 여럿의 직무별 예상 질문**을 보여주고, 보낸 뒤에는 B로 실제 오해가 생겼는지까지 확인합니다.

### D. 직무 + 언어 동시 번역
- **하는 일:** 받는 사람의 언어 설정까지 반영해서 관점 번역과 외국어 번역을 한 번에 처리합니다.
- **예시:** 한국인 기획자의 "결제 플로우 좀 간소화해 주세요" → 해외 개발자에게는 영어로, 단계 수 축소 요구사항과 완료 기준이 정리된 형태로 전달
- **차별점:** 기존 번역 기능(Slack, 잔디, 네이버웍스)은 언어만 바꿉니다.
- **발표 포인트:** 해외 개발팀, 외주팀, 다국적 팀 사례로 글로벌 심사단의 공감을 얻을 수 있습니다.

## 5. 추가 기능 (향후 계획)

- **C. 결론 → 할 일 자동 생성:** B로 합의가 확인된 뒤 직무별 할 일로 변환합니다. Zapier, Slackbot과 겹치므로 B와 연결된다는 점을 차별점으로 삼습니다.
- **F. CS·영업 → 개발 변환:** 개발 직군 밖으로 시장을 넓히는 기능입니다.
- **G. 오해 지도 + 팀 용어집:** 사용자가 등록한 프로필·용어집, "더 쉽게/더 자세히" 피드백, B의 확인 응답과 오해 유형 통계만 데이터 후보로 검토합니다. Slack 메시지 원문을 장기 저장하거나 모델 학습에 쓰는 계획은 제외합니다. 앱에서 생긴 응답·통계도 Slack 데이터에서 파생될 수 있으므로, [Slack API 약관](https://slack.com/terms-of-service/api)과 개발자 정책에서 저장·활용 허용 범위를 확인하기 전에는 축적이나 재사용을 약속하지 않습니다. 검증된 통계만 해당 팀 참여자에게 제공하며, 개인 평가용 관리자 지표는 제공하지 않습니다.

## 6. 데모 범위 제안 (서류 11/15, 온라인 발표 11/20)

| 우선순위 | 기능 | 이유 |
|---|---|---|
| 1 | 기본 맞춤 번역 (프로필 3명) | 핵심 가치. 같은 메시지가 세 가지로 바뀌는 장면 |
| 2 | B. 오해 탐지 | 대표 기능이자 가장 새로운 기능. 미리 준비한 스레드로 시연 |
| 3 | A. 보내기 전 점검 | 이해하기 쉽고 시각적으로 강함. 경쟁이 있어 B의 예방 단계로 보여줌 |
| 4 | D. 언어 동시 번역 | 프로필에 언어 항목만 추가하면 되어서 구현 비용이 적음 |
| - | C, F, G | 신청서에 화면 시안이나 한 줄 계획으로만 제시 |

- **형태:** Slack 앱 (메시지 메뉴 버튼 + 보내기 전 점검 명령어)
- **AI:** 범용 AI API에 프로필 정보와 직무별 출력 형식을 넣어서 처리. 직접 모델을 학습시킬 필요는 없음
